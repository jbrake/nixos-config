FRAMEWORK 13 INTEL PLASMA LAG: WHAT HAPPENED AND HOW TO REMOVE THE WORKAROUND
=============================================================================

Last updated: August 11, 2026
Working branch: debug/intel-plasma-lag
Main commit from which it was created: 475d439


SHORT VERSION
-------------

The new Framework 13 Intel laptop was not inherently slow, and the fresh KDE
installation proved that the hardware could run Plasma normally. The severe
panel, application-menu, and Wi-Fi popup latency appeared after loading this
Nix configuration.

Our testing narrowed the regression to the newer Plasma/userspace package set,
not Linux 7.1.7. The working configuration therefore keeps the complete Intel
userspace on a known-smooth Nixpkgs snapshot while continuing to use the latest
kernel and Linux firmware from the normal nixos-unstable input.

The resulting Intel system is:

  Plasma/KWin:       6.6.5 (known smooth)
  Linux kernel:      7.1.7 (current at the time of testing)
  Linux firmware:    from the current nixos-unstable input
  Intel userspace:   Nixpkgs commit a0374025a863d007d98e3297f6aa46cc3141c2f0

This is not NixOS stable. It is a temporary, known-good unstable snapshot for
the Intel laptop's userspace. The AMD laptop, VMs, and other configurations
continue to use the normal current nixos-unstable package set.


SYMPTOMS
--------

On the Framework 13 Intel Core Ultra laptop:

  * The bottom Plasma panel occasionally flickered blue.
  * Opening the application menu or Wi-Fi popup took roughly a second.
  * General Plasma interaction felt delayed.
  * The system felt substantially better only on the Performance power profile.
  * A fresh KDE/NixOS installation ran smoothly.
  * Loading this repository's newer package set made the problem return.

That last comparison was important: it showed that the laptop and fresh Plasma
configuration were capable of running correctly, and that the regression was
introduced by some part of the newer Nix package set.


WHAT WE TESTED
--------------

1. Intel graphics/kernel parameter experiment

   The running kernel logged an Intel xe-driver selective-fetch warning. We
   tested disabling that feature with a kernel parameter. It did not fix the
   lag, so the parameter was removed.

2. Plasma Manager

   We temporarily prevented Plasma Manager from applying its activation and
   autostart state on the Intel system. The lag remained. Plasma Manager was
   restored, and there is no surviving diagnostic change for it.

3. Known-smooth complete package set

   We rebuilt using the package set retained by the smooth stock generation:

     Nixpkgs:  a0374025a863d007d98e3297f6aa46cc3141c2f0
     Plasma:   6.6.5
     Qt:       6.11.0
     Kernel:   7.0.12

   This was smooth.

4. New userspace with the old kernel

   We then tested the regressed/current Plasma 6.7.4 userspace with the exact
   old 7.0.12 kernel. It was still slow. This was the strongest evidence that
   Linux 7.1.7 was not the cause of the Plasma UI latency.

5. Plasma 6.7.3-only pin

   We investigated pinning only KDE/Plasma to 6.7.3 while keeping all other
   packages current. NixOS then crossed Qt/KDE package-set boundaries in SDDM
   and other applications. It caused mismatched Qt closures and large local
   rebuilds. We stopped this approach because it was too brittle for a normal
   daily configuration.

6. Final working arrangement

   We kept the entire known-smooth userspace together and imported only the
   current kernel and linux-firmware package into the Intel configuration.
   Kernel and firmware are clean package boundaries; mixing an entire KDE/Qt
   desktop across Nixpkgs revisions is not.

   The final build was verified to contain:

     plasma-workspace 6.6.5
     kwin             6.6.5
     Linux kernel     7.1.7


WHAT CHANGED IN THE REPOSITORY
------------------------------

flake.nix:

  * Added nixpkgs-intel-known-good at the exact smooth Nixpkgs commit.
  * Allowed host builders to accept a per-host Nixpkgs input.
  * Assigned only framework-intel-core-ultra to the known-good input.
  * Left the normal nixpkgs input tracking nixos-unstable.

hosts/framework-intel-core-ultra/configuration.nix:

  * Selects linuxPackages_latest from the normal current nixpkgs input.
  * Selects linux-firmware from the normal current nixpkgs input.
  * Leaves the rest of the Intel system on nixpkgs-intel-known-good.

flake.lock:

  * Records both the current nixos-unstable revision and the exact known-good
    Intel revision.

hosts/framework-intel-core-ultra/hardware-configuration.nix:

  * Contains the root and boot filesystem UUIDs from the new installation.
  * These UUID changes belong to the actual machine and must not be discarded
    when cleaning up the debug work.

home/jason/home.nix:

  * Declares the Intel touchpad's Plasma settings using Plasma Manager's typed
    input options rather than raw KDE configuration keys.
  * Keeps the desired behavior separate from the device identity. If the
    laptop or touchpad changes later, add or replace only the name, vendor ID,
    and product ID in touchpadDevices.


GETTING OFF THE DEBUG BRANCH NOW
--------------------------------

The debug branch is only where the repair was developed. There is no reason to
run from that branch forever. Once the current system has been confirmed smooth,
commit the working state and fast-forward it into main.

From the repository root, first review the changes:

  git status
  git diff --check
  git diff

Commit the working configuration, including this document and the new laptop's
correct filesystem UUIDs:

  git add flake.nix flake.lock \
    home/jason/home.nix \
    hosts/framework-intel-core-ultra/configuration.nix \
    hosts/framework-intel-core-ultra/hardware-configuration.nix \
    INTEL-PLASMA-WORKAROUND.txt
  git commit -m "work around Plasma lag on Intel Framework"

Move main forward to the tested commit:

  git switch main
  git merge --ff-only debug/intel-plasma-lag

If desired, publish main and remove the now-finished local debug branch:

  git push origin main
  git branch -d debug/intel-plasma-lag

After that, use main normally. The workaround will be on main, but it remains
Intel-only. The name of the old development branch has no effect on the system.


NORMAL UPDATES WHILE THE WORKAROUND IS ACTIVE
---------------------------------------------

Normal updates of the primary nixpkgs input can continue:

  nix flake update nixpkgs

This updates the AMD laptop and other normal profiles. On the Intel laptop it
also updates the kernel and linux-firmware, but it does not move the pinned
Plasma/userspace snapshot.

Always build before installing:

  nixos-rebuild build --flake .#framework-intel-core-ultra

For system-stack tests, prefer boot rather than switch. It creates a new boot
generation without replacing the currently running Plasma session in place:

  sudo nixos-rebuild boot --flake .#framework-intel-core-ultra
  reboot

If an update fails, choose the previous NixOS generation from the systemd-boot
menu. Do not garbage-collect old generations until the new one is proven good.


WHEN TO TEST A NEWER PLASMA
---------------------------

The bad tested version was Plasma 6.7.4. Do not retest merely because unrelated
packages changed. Wait until nixos-unstable contains a Plasma version newer than
6.7.4, preferably 6.7.5 or 6.8.x.

Check the version available from nixos-unstable without changing the repo:

  nix eval --raw \
    github:NixOS/nixpkgs/nixos-unstable#kdePackages.plasma-workspace.version

If that still prints 6.7.4, keep using the workaround.


HOW TO TEST CURRENT PLASMA SAFELY
--------------------------------

Start only from a clean, committed main branch:

  git switch main
  git status
  git switch -c test/intel-current-plasma

Update the normal current package input:

  nix flake update nixpkgs

In flake.nix, temporarily change the Intel host from:

  nixpkgsInput = inputs.nixpkgs-intel-known-good;

to:

  nixpkgsInput = nixpkgs;

That tests one complete current Nixpkgs package set. It intentionally does not
mix an older KDE with newer Qt or vice versa.

Confirm what will be built:

  nix eval --raw \
    .#nixosConfigurations.framework-intel-core-ultra.pkgs.kdePackages.plasma-workspace.version
  nix eval --raw \
    .#nixosConfigurations.framework-intel-core-ultra.config.boot.kernelPackages.kernel.version

Build the test:

  nixos-rebuild build --flake .#framework-intel-core-ultra

If the build succeeds, commit the temporary test branch so that switching back
to main cannot accidentally carry test changes with it:

  git add flake.nix flake.lock
  git commit -m "test Intel Framework on current Plasma"

Install it only for the next boot, then reboot:

  sudo nixos-rebuild boot --flake .#framework-intel-core-ultra
  reboot

Test the panel, application launcher, Wi-Fi popup, System Settings, window
animations, and all three power profiles. A quick glance is not enough; use the
desktop normally for a while and watch for the blue panel flicker.


IF THE NEW PLASMA IS STILL BAD
------------------------------

1. Reboot and select the previous known-good NixOS generation in systemd-boot.
2. Return to the repository and switch back to main:

     git switch main

3. Do not merge test/intel-current-plasma.
4. The failed test branch can remain as a record or be deleted later:

     git branch -D test/intel-current-plasma

Deleting that Git branch does not delete the bootable NixOS generation. Keep
the older system generation until the machine is unquestionably stable.


IF THE NEW PLASMA IS GOOD
-------------------------

The temporary compatibility pin can then be removed completely. On the test
branch:

  1. Remove the nixpkgs-intel-known-good input from flake.nix.
  2. Remove this Intel-host line:

       nixpkgsInput = inputs.nixpkgs-intel-known-good;

     With that line absent, the builder's default is the normal current
     nixpkgs input.

  3. In hosts/framework-intel-core-ultra/configuration.nix, remove the
     currentPkgs definition and linux-firmware overlay. Change the kernel line
     back to:

       boot.kernelPackages = lib.mkDefault pkgs.linuxPackages_latest;

  4. Remove inputs from that module's argument list if it is no longer used.
  5. Run:

       nix flake lock
       nixos-rebuild build --flake .#framework-intel-core-ultra

  6. Commit the cleanup, boot it once more, and verify it.
  7. Fast-forward the successful test branch into main:

       git switch main
       git merge --ff-only test/intel-current-plasma

At that point the Intel laptop is fully back on the normal current unstable
package set. The generic per-host nixpkgsInput builder support may remain; it is
harmless and useful for future hardware-specific regressions. It may also be
removed later as ordinary cleanup.


EXPECTED WARNING
----------------

While this workaround is active, evaluation reports that Home Manager 26.11 is
being used with a Nixpkgs snapshot identifying as 26.05. The configuration does
build and the working desktop has been tested, but this warning is another
reason to treat the pin as temporary rather than permanent. Do not merely hide
the warning. Remove the compatibility pin once a newer complete package set is
confirmed smooth.


BOTTOM LINE
-----------

The evidence says Plasma/userspace regressed; it does not say that the new Intel
kernel must be held back. The current setup preserves the newest kernel and
firmware for the new hardware while using a complete desktop package set already
proven smooth. Merge this tested workaround into main now, continue normal
kernel/firmware updates, and test a complete newer Plasma package set on a short-
lived branch after nixos-unstable moves beyond Plasma 6.7.4.
